# NADE API — the canonical contract

This document is the single source of truth for every byte on the wire between
the Rust backend and the iOS app. `docs/PLAN.md` describes *what we are
building*; this describes *exactly what it looks like*. Where the two disagree,
this file wins.

The rule that makes it work: **a shape change touches `docs/contract/` first.**
Backend tests serialise their real response types and compare against those
fixtures; iOS tests decode the same files. Drift is a failing test on both
sides rather than a runtime surprise.

Fixtures are generated by `docs/contract/generate.py` from one coherent world
state, so ids, statuses and cross-references cannot contradict each other.
Edit the generator, never the JSON.

---

## 0. Conventions

**Base** `/v1`. **Auth** `Authorization: Bearer <token>` on every route except:

| Route | Why it cannot carry a bearer, and what guards it instead |
|---|---|
| `GET /healthz` | Liveness must answer before anything else works. Returns nothing sensitive. |
| `POST /auth/pair` | It is how a token is obtained. Guarded by a single-use 6-digit code with a 10-minute TTL and a 10/minute rate limit. |
| `GET /auth/gmail/start`, `GET /auth/gmail/callback` | **Browser-facing** — a redirect and a Google callback, neither of which can set a header. Guarded by a single-use `state` with PKCE, a bounded in-flight set, and a refusal to bind a second Google account. |
| `POST /webhooks/gmail` | Pub/Sub cannot present a bearer. Guarded by full OIDC verification — JWKS signature, `iss`, `aud`, `email == PUSH_SA_EMAIL`, `email_verified`. |

**Time** ISO-8601 UTC, second precision, always `Z`-suffixed:
`2026-08-16T09:12:04Z`. Never a local offset, never milliseconds. The iOS side
decodes with a fixed formatter, not `.iso8601` with fractional seconds.

**Ids**

| Kind | Form | Notes |
|---|---|---|
| account, agent, run, note, draft, feed item, device | UUID, hyphenated, lowercase | |
| message | Gmail message id (`"18f2a1b3c4d5e6f7"`) | The database's `messages.id` bigint is internal and **never appears on the wire.** |
| thread | Gmail thread id | |
| mailbox | Gmail label id (`"INBOX"`, `"Label_25"`) | |
| attachment | Gmail attachment id | Opaque, long, may contain `-` and `_`. |
| bearer token | `nade_` + 64 lowercase hex chars | 32 random bytes. Total length 69. |
| approval token | UUID | Single-use. |

**Nullability is explicit everywhere in this document.** A field marked
`string|null` is always present and may be null. A field with no `|null` is
always present and never null. Nothing is ever omitted — the iOS models can use
non-optional properties wherever this document does.

**Pagination is per-endpoint, not universal.** A response carries
`next_cursor: string|null` **if and only if** it is listed as paginated below.
Bounded collections — mailboxes, agents, settings — return a plain array with
no cursor field at all, because inventing one implies a page boundary that will
never exist.

| Endpoint | Paginated | Page size |
|---|---|---|
| `GET /mailboxes` | no | — |
| `GET /agents` | no | — |
| `GET /mailboxes/{id}/threads` | yes | `limit`, default 50, max 100 |
| `GET /search` | yes | 50 |
| `GET /notes` | yes | 50 |
| `GET /drafts` | yes | 50 |
| `GET /feed` | yes | 50 |
| `GET /runs` | yes | 50 |

A cursor is an opaque base64url string. **Clients must not parse it, and its
contents differ per endpoint** — the guarantees below are the endpoint's, not
the cursor format's. An unknown or corrupt cursor is `400 bad_request`, never a
silent reset to page one.

- **List endpoints over our own rows** (threads, notes, drafts, feed, runs) use
  a **keyset** cursor — the `ts` and `id` of the last row — so a row inserted
  mid-scroll can neither duplicate nor skip an item.
- **`GET /search` wraps Gmail's `pageToken`** and inherits whatever paging
  guarantees Gmail gives. A `pageToken` is scoped to the query that produced
  it, so a cursor is only valid with the same `q`; the query is fingerprinted
  into the cursor and a mismatched pair is `400 bad_request` rather than a
  confusing upstream failure.

The last page has `next_cursor: null`. An empty collection returns an empty
array **and** `next_cursor: null` — never `404`.

**Errors** always `{"error": {"code": "...", "message": "..."}}`. `message` is
end-user-facing English: it says what happened and what to do, never a stack
trace, never an internal identifier. `code` is the stable machine value:

| code | HTTP | Meaning |
|---|---|---|
| `bad_request` | 400 | Malformed body, unknown cursor, invalid parameter. |
| `unauthorized` | 401 | Missing, unknown, revoked, or expired credential; also a wrong or spent pairing code. |
| `forbidden` | 403 | Authenticated but not permitted (reserved; v1 is single-account). |
| `not_found` | 404 | No such resource, or not this account's. |
| `conflict` | 409 | State moved on: `token_consumed`, duplicate device. |
| `token_consumed` | 409 | This approval was already recorded. **Clients treat it as success.** |
| `gone` | 410 | The resource existed and expired. |
| `approval_expired` | 410 | This approval passed its deadline. |
| `payload_too_large` | 413 | Body or attachment over the cap. |
| `rate_limited` | 429 | Too many attempts; `Retry-After` header set. |
| `needs_reauth` | 409 | Gmail credentials are dead; the user must re-consent. |
| `upstream_unavailable` | 502 | Gmail or the model provider failed after retries. |
| `internal` | 500 | Anything else. Never leaks detail. |

**Rate limits** apply to `POST /auth/pair` (10 per minute per process) and
`POST /ask` (30 per minute). Both answer `429` with `Retry-After` in seconds.

**Caps** request body 1 MB, attachment download 25 MB, `q` 512 chars,
`nl_definition` 4 000 chars, `device_name` 64 chars, note body 256 KB.

## 1. Auth and identity

### `POST /auth/pair`

Unauthenticated. Exchanges the one-time code the server prints on startup for a
device token.

```json
→ {"code": "203120", "device_name": "jatin-iphone"}
← {"token": "nade_cfa3abd9…"}                                            // 69 chars
```

`code` is a **string**, not a number — it can have a leading zero. Six ASCII
digits; anything else is `400 bad_request`. The code is single-use with a
10-minute TTL; a wrong, expired, or already-spent code is `401 unauthorized`
with the standard envelope, deliberately indistinguishable so the response
cannot be used as an oracle. Attempts are rate limited to 10/minute.

Only `sha256(token)` is stored, in `devices.bearer_hash`. The plaintext token
exists exactly once, in this response.

### `GET /me`

```json
← {"email": "jatinsethi98@gmail.com", "status": "ok"}
```

`status` ∈ `ok` | `needs_reauth`. When `needs_reauth`, Gmail sync is paused and
the client shows the re-sign-in row in Settings.

**Before any Gmail account is connected** this returns
`{"email": "", "status": "needs_reauth"}` — a 200, not a 404. A freshly paired
device asking "who am I?" is not an error, and the state it needs to render is
exactly the state it renders after a token dies: the same re-sign-in row. A 404
would force the client to carry a third case that behaves identically to the
second.

### `GET /auth/gmail/start`

`302` to Google, carrying PKCE + `state`. The callback
(`/v1/auth/gmail/callback`) is browser-facing, binds the returned account to
the single `accounts` row, and renders a plain "you can close this tab" page.
Used both for first connection and for re-consent.

## 2. Mail

### `GET /mailboxes`

Not paginated.

```json
← {"mailboxes": [{"id": "INBOX", "name": "Inbox", "kind": "system",
                  "unread": 12, "total": 201}, …]}
```

`kind` ∈ `system` | `user`.

**Gmail's own system labels have `name == id`** (`CATEGORY_PERSONAL`), which is
not a thing to show a person. The server maps them, and **only these system
labels are exposed** — the rest (`UNREAD`, `IMPORTANT`, `CHAT`, `YELLOW_STAR`,
`SPAM`, `TRASH`, `DRAFT`) are flags or places v1 does not sync:

| Gmail id | `name` | Order |
|---|---|---|
| `INBOX` | Inbox | 1 |
| `CATEGORY_PERSONAL` | Primary | 2 |
| `CATEGORY_UPDATES` | Updates | 3 |
| `CATEGORY_SOCIAL` | Social | 4 |
| `CATEGORY_PROMOTIONS` | Promotions | 5 |
| `CATEGORY_FORUMS` | Forums | 6 |
| `STARRED` | Starred | 7 |
| `SENT` | Sent | 8 |

User labels follow, `name` passed through from Gmail verbatim — including the
awkward real ones (`[Notion]`, `[Gmail]All Mail`) — **ordered by raw byte value
of the name**, not by locale collation. Byte order is stable across platforms
and Postgres collations; a locale-aware sort is not, and the iOS list would
disagree with the server's on some devices. Labels whose name starts with
`[Gmail]` are hidden: they are Gmail's own internal views, not places.

`unread` and `total` count **threads**, not messages, because that is what the
list shows. Both are within the synced 30-day window; they are not Gmail's
totals and the client must not present them as mailbox-wide truth.

**Unread is Gmail's, and v1 cannot change it.** A thread is unread when any of
its messages still carries Gmail's `UNREAD` label. Opening a thread in NADE
does **not** clear it: v1 holds `gmail.readonly` and takes no outbound actions,
so removing a label is not something it can do. The dot therefore reflects the
true state of the mailbox and clears when the user reads the mail in Gmail and
the next sync lands.

This is deliberate, and the client must **not** paper over it with a local
read-marker. A local flag would disagree with Gmail within minutes and the user
would have two contradictory inboxes — the exact failure this app exists to
avoid. (Note the contrast with `notes.unread`, which *is* NADE's own state
about NADE's own data, and is therefore ours to clear.)

### `GET /mailboxes/{id}/threads?cursor&limit`

Paginated. Sorted by `ts` descending, then `id` descending as a tiebreak, so
the keyset cursor is total.

```json
← {"threads": [{
     "id": "18f2a1b3c4d5e6f7",
     "subject": "Staff Product Designer at Kettle",     // "" when the mail has none
     "snippet": "Hi Jatin — I came across…",            // ≤ 200 chars, whitespace-collapsed
     "from_name": "Priya Raghavan",                     // "" when the sender had no display name
     "from_email": "priya@kettle.com",
     "ts": "2026-08-16T09:12:04Z",                      // newest message in the thread
     "unread": true,                                    // ANY message in the thread is unread
     "msg_count": 1,
     "agent_note": "Job Search Tracker · two next steps to approve"   // string|null
   }, …],
   "next_cursor": "eyJ0cyI6…"}
```

`from_name`/`from_email` are the **newest** message's sender, matching what the
list shows. `from_name` is `""` rather than null when absent — the UI decides
whether to fall back to the address; the server does not invent one.

`agent_note` is the one-line summary of the most recent agent run touching this
thread that still wants something, or null. It is exactly the string the mail
row renders under the snippet.

### `GET /threads/{id}`

```json
← {"id": "18f2a1b3c4d5e6f7",
   "subject": "Staff Product Designer at Kettle",
   "mailbox_name": "To Reply",              // the label the thread is filed under, for the footer
   "account_email": "jatinsethi98@gmail.com",
   "messages": [{
     "gmail_id": "18f2a1b3c4d5e6f7",
     "from_name": "Priya Raghavan",
     "from_email": "priya@kettle.com",
     "to": ["jatinsethi98@gmail.com"],       // may be empty (undisclosed-recipients)
     "cc": [],
     "ts": "2026-08-16T09:12:04Z",
     "body_text": "Hi Jatin — …",            // never null; may be "" for a genuinely empty body
     "body_html": "<div>…</div>",            // string|null — null when NO text/html part exists
     "label_ids": ["INBOX", "UNREAD", "Label_25"],
     "attachments": [{"id": "ANGjdJ_qk…", "name": "Kettle — Staff Designer.pdf",
                      "mime": "application/pdf", "size": 245760, "inline": false}]
   }, …],
   "agent_cards": [{"run_id": "…", "agent_name": "Job Search Tracker",
                    "status": "pending_approval", "summary": "Two next steps found…",
                    "feed_item_id": "…"}],   // feed_item_id: string|null
   "partial": false}                         // true ⇒ `messages` is not the whole conversation
```

There is **no `id` field on a message.** `gmail_id` is the identity. The
database's bigint primary key is internal.

`body_text` is guaranteed non-null: 47% of real mail in this account carries no
`text/plain` part at all, so it is synthesised from the HTML (see
`backend/testdata/mime/README.md`). `body_html` is null when the message
genuinely has no `text/html` part — it is **not** a rendering of the plain text.
The "View original" affordance keys off `body_html != null`.

`inline` marks a part referenced by `cid:` from the HTML. `cid:` URLs inside
`body_html` are rewritten server-side to
`/v1/messages/{gmail_id}/attachments/{att_id}` before the response is built.

`messages` is ordered oldest first. `agent_cards` is ordered newest first.

**`partial` is how the windowed cache tells the truth.** Postgres holds a recent
window plus whatever has been looked at, never the mailbox (`docs/SEARCH.md`), so
a thread can be present with only some of its messages — a search that matched
one message of a ten-message conversation cached exactly that one. Opening a
thread therefore asks Gmail for the thread's full message list and fetches what
is missing, once; from then on it is a local read. `partial` is `true` only when
that completion could not finish — Gmail unreachable, throttled, or a credential
that needs re-auth — and it means *what you are reading has gaps*. Clients must
surface it rather than render the rows as a complete thread. `msg_count` in the
list is the count within the window; after a thread has been completed it is
Gmail's own count.

### `GET /messages/{gmail_id}/attachments/{att_id}`

Streams the bytes with `Content-Type` from the stored metadata and
`Content-Disposition: attachment; filename*=UTF-8''…`. Bytes are **not** stored
in Postgres; the server fetches them from Gmail on demand and does not cache
them. Over 25 MB → `413 payload_too_large`. Gmail no longer has the message →
`404 not_found`.

### `GET /search?q&cursor`

Same body shape as the threads list. **Search is delegated to Gmail** — see
`docs/SEARCH.md` for why. `q` goes to `users.messages.list`, the returned ids
are hydrated from our rows, misses are batch-fetched and cached, and the page
comes back in **Gmail's relevance order, not date order**. It therefore covers
the whole mailbox, not the synced window.

`q` is **validated before it is sent**, and a refusal explains itself. Gmail
never answers a bad query with a 400 — it answers with an empty 200 — so a
malformed query is otherwise indistinguishable from "no such mail". The
validator refuses what Gmail would silently swallow: unknown operators, an
operator with an empty argument (which matches *everything*), unsupported
`newer_than` units, and a lowercase `or` (which is matched as a literal word
and narrows the result to nothing). It normalises what is recoverable —
operator names fold case, a space after a colon is absorbed, and a **label id
is translated to its name**, since `q=label:` takes names and matches nothing
given an id.

Empty or whitespace-only `q` → `400 bad_request`. No results is an empty array,
not a 404.

**Errors**, beyond the shared set: `400 bad_request` for a rejected query, a
corrupt cursor, or a cursor paired with a different query; `502
upstream_unavailable` when Gmail fails after retries; `409 needs_reauth` when
the credential is dead. A client that cannot reach search must say so rather
than presenting locally-filtered rows as a complete result.

Two consequences worth stating, because both surprise:

- **A page of 50 is an upper bound on threads, not a count.** Gmail pages
  *messages*, and several may share a thread.
- **Hydrated old mail joins the mailbox lists** at its original date — that is,
  at the bottom. It follows from the cache holding anything we have looked at.

A whole batch failing while hydrating is a `502`: a page missing ten of its
results is not a result. A single message failing is logged and skipped, so the
page is one row shorter.

## 3. Notes and drafts

v1 agents write notes and prepare drafts. Neither ever leaves the server: a
draft is a NADE draft, not a Gmail draft.

### `GET /notes?q&cursor`

Paginated. `q` optional.

Notes are **our** rows, so Gmail cannot search them, and `docs/SEARCH.md`
forbids standing up a second index. `q` is therefore a plain case-insensitive
substring predicate over `title` and `body_md` — a sequential scan, deliberately.

That is correct rather than lazy: a note is written by an agent run, and the
dev caps bound runs to a handful a day, so this table holds tens of rows and
will hold hundreds. Indexing hundreds of rows costs more than scanning them.
If it ever passes ~10,000, revisit — and revisit with `pg_trgm`, not with a
tsvector, since substring is what the UI's "Search notes" box actually means.

```json
← {"notes": [{"id": "…", "run_id": "…"|null, "thread_id": "…"|null,
              "title": "Kettle — next steps",
              "agent_name": "Job Search Tracker",   // string|null
              "unread": true,                        // agent wrote it, you have not opened it
              "updated_at": "2026-08-16T09:13:58Z"}, …],
   "next_cursor": null}
```

`agent_name` is null for a note with no run behind it. `unread` drives the gold
left rule in the list; it flips to false on `GET /notes/{id}`.

### `GET /notes/{id}`

```json
← {"id": "…", "title": "…", "body_md": "# Kettle…", "run_id": "…"|null,
   "thread_id": "…"|null, "agent_name": "…"|null, "unread": false,
   "updated_at": "…"}
```

Reading a note marks it read. The response therefore always shows
`unread: false` — it reports the state *after* the read.

### `GET /drafts?cursor` · `PATCH /drafts/{id}`

```json
← {"drafts": [{"id": "…", "run_id": "…"|null, "thread_id": "…"|null,
               "to": ["priya@kettle.com"], "subject": "Re: …",
               "body_text": "…", "created_at": "…", "updated_at": "…"}],
   "next_cursor": null}

PATCH → {"to"?: [...], "subject"?: "...", "body_text"?: "..."}
     ← the full draft
```

`PATCH` accepts any subset; an empty object is `400 bad_request`. Each address
in `to` must contain `@` or the request is `400`.

## 4. Ask

### `POST /ask`

```json
→ {"query": "what did Priya say about next steps?",
   "thread_id": "…"|null,
   "route_hint": "answer"|"results"|"agent_draft"|null}
```

`route_hint` forces the route instead of letting the server classify. It exists
because the design has a button that cannot otherwise work: the results state
offers **"Make this an agent"**, and with server-side classification alone
there is no way for the client to say "I know what this is, build the agent."
The server honours a hint rather than re-guessing. `null` — the normal case —
means classify.

Responds `text/event-stream`. **The first event is always `route`.** Every
stream ends with exactly one terminal event: `done` **or** `error`, never both,
and nothing follows it.

```
event: route
data: {"kind":"answer"|"results"|"agent_draft"}
```

**`kind: "answer"`** — a prose answer.
```
event: token   data: {"text":"Priya "}          # zero or more, in order
event: done    data: {"sources":[{"gmail_id":"…","subject":"…"}]}
```

**`kind: "results"`** — a search. The design renders a prose lead-in *above* the
hits, so this stream carries both: tokens first, then the hits.
```
event: token   data: {"text":"Seven bookings this year. "}   # zero or more
event: results data: {"threads":[ … threads-list shape, no cursor … ]}
event: done    data: {"sources":[]}
```

**`kind: "agent_draft"`** — a proposed agent. The design underlines the two
editable spans, so they are sent as separate fields rather than left for the
client to find in a sentence.
```
event: draft data: {"name":"Recruiter Next Steps",
                    "nl_definition":"When a recruiter emails…",
                    "when_span":"a recruiter emails about a tech role",
                    "do_span":"save the next steps as a note",
                    "trailing":"Asks before it saves."|null,
                    "tool":"write_note",
                    "approval_required":true,
                    "status":"draft"}
event: done  data: {"sources":[]}
```
The client renders `When {when_span}, {do_span}.` with both spans underlined,
then the trailing muted clause. Saving posts `nl_definition` to `POST /agents`.

**Errors mid-stream**
```
event: error data: {"code":"upstream_unavailable","message":"…"}
```
May follow partial `token` events — the client keeps what it received and shows
the error beneath it. `done` does **not** follow `error`. The stream is not
resumable: retrying means a fresh `POST /ask`. Idle timeout 300 s.

Routing is decided server-side: heuristics first (a quoted phrase or a
`from:`/`to:`/`has:` operator → `results`; an imperative "when…"/"every…" →
`agent_draft`), then a cheap model for the remainder.

`GET /search` still exists and is what the Mail tab's plain search box uses.

## 5. Agents

### `GET /agents`

Not paginated. Ordered **oldest first** by `created_at`, so the list does not
reshuffle under the user every time an agent runs.

```json
← {"agents": [{
     "id": "…", "name": "Job Search Tracker",
     "nl_definition": "When a recruiter emails about a tech role, …",
     "status": "published",                  // draft | published | paused
     "trigger_summary": "On new mail",       // human string, server-rendered
     "schedule": {…}|null,
     "last_run_at": "2026-08-16T09:13:41Z"|null,
     "approval_required": true
   }, …]}
```

### `POST /agents`

```json
→ {"nl_definition": "When a recruiter emails about a tech role, …"}
← the full agent object (below)
```

**A newly created agent is always `status: "draft"`.** The client cannot ask for
anything else, and a draft never runs. This is what the Ask screen promises
("Saved to Agents as a draft. It won't run until you publish it."), so it is
enforced server-side rather than trusted to the caller. Publishing is a
separate `PATCH`.

Creation compiles `nl_definition` into `spec` with the strong model. If
compilation fails, the agent is still created as a draft with `spec: null` and
`compile_error` set, so the user's sentence is never lost.

### `GET /agents/{id}` · `PATCH /agents/{id}` · `DELETE /agents/{id}`

The full agent object adds:

```json
{ …list fields…,
  "allowed_tools": ["search_mail", "read_thread", "write_note"],
  "when_span": "a recruiter emails about a tech role",   // string|null
  "do_span": "save the next steps as a note",            // string|null
  "trailing": "Ask me before you save."|null,
  "compile_error": null,                     // string|null
  "spec": { … §5.1 … }|null }
```

`when_span` / `do_span` / `trailing` are the same three fields the `agent_draft`
SSE event carries, and they exist for the same reason: the builder screen
renders **"When {when_span}, {do_span}."** with both spans underlined and
tappable. Without them on the agent object, an agent could be underlined when
first drafted and not after it was saved — the screen would quietly change
behaviour depending on where you arrived from. They are derived from `spec` at
compile time and are null when `spec` is null.

`PATCH` accepts any subset of
`nl_definition`, `status`, `allowed_tools`, `approval_required`, `schedule`.
Changing `nl_definition` recompiles `spec`. `runs_done` is server-maintained
and is **ignored** if sent. `DELETE` → `204`; in-flight runs are left to finish
and their feed items remain readable.

### 5.1 The compiled `spec`

```json
{
  "version": 1,
  "trigger": {
    "kind": "mail" | "schedule" | "manual",
    "filters": {                              // deterministic SQL prefilter; all optional, all ANDed
      "from_domains": [], "from_contains": [], "subject_contains": [],
      "body_contains": [], "label_ids": ["INBOX"],
      "has_attachment": null,                 // bool|null
      "newer_than_days": 30
    },
    "semantic": "The sender is a recruiter…"|null    // only reached by rows the filters kept
  },
  "instruction": "Read the thread. Extract every concrete next step…",
  "tools": ["search_mail", "read_thread", "write_note"],
  "output": {"kind": "note"|"draft"|"none", "title_template": "{company} — next steps"|null}
}
```

`spec.tools` must be a subset of `allowed_tools`; the host enforces
`allowed_tools` at dispatch regardless of what the spec says. v1's entire tool
set is `search_mail`, `read_thread`, `write_note`, `draft_reply`.

### 5.2 The schedule

```json
{"freq": "day"|"week"|"month",
 "interval": 1,                     // ≥ 1
 "byweekday": ["mon","tue","wed","thu","fri"],   // freq=week only; [] means "same weekday as the anchor"
 "bymonthday": 1,                   // freq=month only; 1..28, or -1 for "last day". null → anchor's day
 "at": "08:00",                     // 24h local wall-clock, always HH:MM
 "tz": "America/Phoenix",           // IANA. Captured from the device at creation; no UI control in v1
 "ends": {"kind": "never"|"on"|"after", "date": "2026-12-31"|null, "count": 10|null},
 "runs_done": 42}                   // server-maintained, read-only
```

Semantics, all of which two implementers would otherwise guess differently:

- `next_run_at` is **derived**, never sent by the client. It is computed with
  `chrono-tz` in `tz`, using **wall-clock** semantics: 08:00 stays 08:00 across
  a DST change.
- **Spring-forward gap** (the instant does not exist): roll forward to the first
  valid instant.
- **Fall-back overlap** (the instant happens twice): take the **first**.
- `bymonthday` is capped at 28 for a fixed day so a monthly schedule never
  silently skips February. `-1` means the actual last day of that month.
- `runs_done` counts runs the **schedule** started, whatever their outcome —
  including failed and skipped ones. Manual runs (`POST /agents/{id}/run`) do
  not count. Editing the agent does not reset it.
- `ends.after.count` is a **total since creation**, compared against
  `runs_done`. On reaching it the agent moves to `status: "paused"` and a feed
  `info` item says so.
- `ends.on.date` is inclusive and interpreted in `tz`.

## 6. Runs

### `GET /runs?agent_id&cursor`

Paginated, newest first. `agent_id` optional. This is the Settings → Run log.

```json
← {"runs": [{"id": "…", "agent_id": "…", "agent_name": "Job Search Tracker",
             "trigger_kind": "mail"|"schedule"|"manual",
             "status": "…", "summary": "Two next steps found…"|null,
             "created_at": "…", "updated_at": "…"}],
   "next_cursor": null}
```

### `GET /runs/{id}`

```json
← {"id": "…", "agent_id": "…", "agent_name": "…", "status": "…",
   "trigger_kind": "mail", "trigger_ref": "18f2c4d5e6f70819"|null,   // see below
   "error": null,                                     // string|null, set when status=failed
   "journal": [{"seq": 1, "kind": "…", "payload": {…}, "created_at": "…"}]}
```

`status` ∈ `queued` `running` `pending_approval` `waiting` `done` `failed`
`expired` `skipped`.

`trigger_ref` is the **message** id for `trigger_kind: "mail"` — the specific
message that fired the run, not its thread. The distinction is invisible on a
one-message thread, where Gmail gives the thread the same id as its first
message, and very visible on the fourth reply. It is null for `schedule` and
`manual`.

### 6.1 Journal entry kinds

**Every entry has its own `seq`.** It starts at **1** and increases by exactly
one with no gaps — `run_journal`'s primary key is `(run_id, seq)`, so two
entries cannot share one.

A *step* is therefore identified by the `seq` of the entry that **opened** it,
and the entries that close it name that seq explicitly:

- an ordinary call is opened by `step_started`;
- a gated call is opened by **`approval_requested`** — the `step_started` that
  eventually executes it is a *later* entry that carries the original opening
  seq forward.

`step_done`, `step_failed` and the executing `step_started` all carry
`step_seq` in their payload, pointing at that opening entry. Correlating by
"the nearest preceding open with the same tool name" would be ambiguous the
moment an agent calls one tool twice, which is ordinary.

`effect_id` is derived from the **opening** seq and from nothing else, so a
gated step keeps the id minted at `approval_requested` right through approval
and execution. That is precisely what makes a post-crash re-execution upsert
instead of duplicating.

Three fields exist purely so a resumed run cannot drift from the one that was
interrupted:

- **`opened_at`** is stamped when the step opens and is replayed, not
  regenerated. Every attempt at a step therefore sees byte-identical input, so
  the same `effect_id` implies the same written value.
- **`tool_fingerprint`** hashes the tool's *interface* — name, description,
  version, schema. It is checked before every dispatch, including after an
  approval, so a step opened under one build cannot execute under another. It
  covers the interface, not the behaviour behind it: a silent behaviour change
  is caught only if the author bumps the tool's version, which is a limit no
  hash can remove.
- **`wake_at`** rides on `step_done` rather than in a following entry, so
  completing a step and recording the pause it asked for are one committed
  write. Split across two, a crash in the gap loses the delay silently.

### 6.2 What the runtime actually guarantees

**At-least-once execution with stable idempotency keys**, conditional on a
durable journal and idempotent effects. Not exactly-once — nothing that
survives a process death can be.

What holds: the intention commits before the act; an interrupted step is
executed again; every attempt gets the same `effect_id` and identical input;
and replay *finishes what is recorded* rather than restarting it. Exactly-once
**effects** are then the consumer's to achieve, by upserting on `effect_id`.

The consequence for NADE: a mutating tool must write its row with
`insert … on conflict (id) do update`, never a plain insert and never a fresh
id. **Human approval is not an idempotency mechanism** — it authorises an
action, it does not make a re-run of that action harmless. An effect with no
natural key needs an outbox keyed on `effect_id` regardless of who approved it.

| `kind` | `payload` |
|---|---|
| `run_started` | `{"trigger_kind": "mail", "trigger_ref": "…"\|null}` |
| `llm_response` | `{"model": "…", "stop_reason": "tool_use"\|"end_turn"\|"max_tokens", "tokens_in": 1840, "tokens_out": 96, "text": "…"}` |
| `step_started` | `{"tool": "read_thread", "step_seq": 3, "opened_at": "…", "args": {…}, "args_hash": "sha256:…", "effect_id": "…", "tool_fingerprint": "sha256:…"\|null}` — `step_seq` equals this entry's own `seq` for an ungated call, or the `approval_requested` seq for a gated one |
| `step_done` | `{"tool": "read_thread", "step_seq": 3, "result": {…}, "result_bytes": 1204, "truncated": false, "wake_at": "…"\|null}` |
| `step_failed` | `{"tool": "…", "step_seq": 3, "error": "…"}` |
| `approval_requested` | `{"tool": "write_note", "feed_item_id": "…", "effect_id": "…", "summary": "…"}` |
| `approval_granted` | `{"feed_item_id": "…"}` |
| `approval_skipped` | `{"feed_item_id": "…"}` |
| `approval_expired` | `{"feed_item_id": "…"}` |
| `waiting` | `{"wake_at": "…"}` |
| `resumed` | `{"after": "approval"\|"timer"\|"crash"}` |
| `cap_exceeded` | `{"cap": "max_steps"\|"token_budget"\|"spend_ceiling", "limit": 12, "actual": 13}` |
| `run_done` | `{"summary": "…"\|null}` |
| `run_failed` | `{"error": "…"}` |

`step_done.result` is the tool's return value, size-capped. When capping bites,
`truncated` is true and the value carries an explicit
`"…[truncated N bytes]"` marker — never a silent trim.

`effect_id` is `uuid5(EFFECT_NAMESPACE, "<run-id>:<seq>")` with the frozen
namespace `6e616465-5f65-6666-6563-745f6e737631` (the ASCII bytes of
`nade_effect_nsv1`). Every row a step writes uses that UUID as its primary key
and is written with an upsert, which is what makes re-execution after a crash
harmless. Notes and drafts created by an agent therefore have **v5** UUIDs;
ones created any other way have v4.

## 7. Feed

The feed is the home screen. It is the only place NADE asks for anything.

### `GET /feed?cursor`

```json
← {"items": [{
     "id": "…",
     "kind": "approval" | "info",
     "title": "Job Search Tracker",          // the agent's name
     "body": "Two next steps found — 30-min intro and portfolio session. Save them as a note?",
     "status": "new" | "resolved" | "skipped" | "expired",
     "run_id": "…"|null,
     "actions": ["approve", "edit", "skip"],  // exactly the buttons to render, in order
     "approval_token": "…"|null,              // non-null only while status=new AND kind=approval
     "approval_expires_at": "…"|null,
     "resolved_note": "Saved to Notes."|null, // the italic line under a resolved item
     "data": {…}|null,                        // typed by data.action, §7.1
     "created_at": "…"
   }, …],
   "next_cursor": null,
   "new_count": 2}
```

`actions` removes the guesswork the design otherwise creates. It is:

- `["approve", "edit", "skip"]` when `kind=approval`, `status=new`, and the
  pending action is `draft_reply` — Edit means *approve, then edit the draft it
  created*, which is the only edit path v1 has.
- `["approve", "skip"]` when `kind=approval`, `status=new`, and the pending
  action is `write_note`. **There is no note editor in v1**, so no Edit button.
- `[]` for anything resolved, skipped, expired, or `kind=info`.

`new_count` is the number of items with `status: "new"` — approvals *and*
unseen info items. It is the badge.

`approval_expires_at` is non-null on **every** `kind: "approval"` item
regardless of status, and null on every `info` item. Keeping it after
resolution is deliberate: it is what lets an expired card say *when* it
expired.

`resolved_note` is the italic line under a card that is finished with. It is
set for `resolved`, `skipped` **and** `expired`, and null for `new` and for
`info`. Skipped and expired need it most — without it those cards render an
outcome with no explanation.

### 7.1 `data`, typed by action

```json
// action = "write_note"
{"action": "write_note", "action_label": "Save note",
 "note_title": "Kettle — next steps", "note_id": "…", "thread_id": "…"|null}

// action = "draft_reply"
{"action": "draft_reply", "action_label": "Save draft",
 "draft_id": "…", "thread_id": "…", "to": ["priya@kettle.com"],
 "subject": "Re: …", "never_messaged": true}     // true → the UI flags the recipient

// kind = "info"
{"action": "none", "note_id": "…"|null, "thread_id": "…"|null}
```

`action_label` is the verb the card shows. It says **"Save note"** or
**"Save draft"** and never "Send": v1 takes no outbound action, and the UI is
not allowed to imply otherwise.

`note_id` and `draft_id` are the **deterministic** `effect_id` of the step
awaiting approval — they exist before the approval, so the client can deep-link
straight after approving without a round-trip to discover the new id.

### `GET /feed/{id}`

The same item shape. This is the push deep-link: the APNs payload carries only
`feed_item_id`, and the client fetches the item — including its
`approval_token` — through its authenticated session.

### `POST /feed/{id}/approve`

```json
→ {"approval_token": "…"}
← {"run_id": "…", "status": "queued"}
```

**One transaction, all of it or none of it:** validate and consume the token →
move the run `pending_approval → queued` with its `pending_action` intact →
move the feed item to `resolved` and set `resolved_note` → append
`approval_granted` to the journal → write an `audit_log` row → enqueue the
resume job. A test asserts all six writes land together.

- Replay with the same token → `409 token_consumed`. **The client treats this
  as success** — it means an earlier attempt already won.
- Past `approval_expires_at` → `410 approval_expired`, the run moves to
  `expired`, and the item's status follows.
- Wrong token → `401 unauthorized`.

Approvals expire **7 days** after creation. A cron sweeps expired ones hourly.

### `POST /feed/{id}/skip`

```json
→ {"approval_token": "…"}
← {"status": "skipped"}
```

Takes the token for the same reason approve does: it is a state change, and a
push-action tap must not be forgeable. Same transactional guarantee — run →
`skipped`, item → `skipped`, `approval_skipped` journalled, audit row written.
Same `409` / `410` / `401` behaviour.

### `POST /feed/seen`

```json
→ {"ids": ["…", "…"]}
← {"new_count": 0}
```

Marks `kind: "info"` items as `resolved`. Without it `new_count` would never
fall, because info items have nothing to approve. Ids that are approvals, or
already resolved, or unknown, are ignored rather than erroring — this is a
best-effort read receipt fired as the user scrolls.

## 9. Devices and push

### `POST /devices`

```json
→ {"apns_token": "…"}
← 204
```

Binds the APNs token to the calling device row. Idempotent.

### APNs payload

```json
{"aps": {"alert": {"title": "Job Search Tracker",
                   "body": "Two next steps found — save them as a note?"},
         "category": "APPROVAL", "sound": "default"},
 "feed_item_id": "c0000001-0000-4000-8000-000000000001"}
```

**No capability, token, or mail content in the push.** Category `APPROVAL`
declares APPROVE and SKIP, both `.authenticationRequired`; both fetch
`GET /feed/{id}` through the authenticated session and post with the token they
find there.

### `POST /webhooks/gmail`

Pub/Sub push. Not bearer-authenticated: it verifies the OIDC token fully —
JWKS signature, `iss`, `aud`, `email == PUSH_SA_EMAIL`, `email_verified`.
Audience alone is forgeable and is not sufficient. Returns `204` fast and does
the work on the job queue; anything else makes Pub/Sub retry.
